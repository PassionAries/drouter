# Drouter arm64 Debian 适配说明

> 适用版本：**v1.0.10**
> 适配日期：2026-10-16
> 本轮适配**只针对一个发行版**（下面第 1 节那台机器），别的 arm64 发行版未经实测。

## 0. 先说清楚这次做了什么、没做什么

有用户提需要在 arm64 的 Debian 上跑 drouter，于是拿了一台 arm64 的 Debian 系
发行版做**纯适配**：把项目里所有写死 x86 假设的地方找出来修掉，
在这个发行版上实测构建与运行，然后把「发行版名 / 内核名 / CPU / 固件 /
板卡」这些机器特征提取出来写进本说明。

**做了**：源码层面的架构无关化修复（见第 3 节）+ 在目标发行版上实测
（见第 2 节）+ 本说明文档。

**没做**（不要被后面的绿勾误导）：

- **没有在目标机上启用 drouter 的 Web 面板与常驻服务**，也没装依赖、没执行任何
  「应用到系统」。目标机的 8080 端口已有别的业务在跑，出于不影响现场业务的前提，
  只做了**只读**验证：构建、渲染、依赖自检、各种探测函数。
- **没有做 NAT / DHCP / PPPoE 的实际转发验证**。那需要在面板上点「应用」，
  会真的改网卡与起服务 —— 本次刻意避开。
- **没有验证除下面这台以外的任何 arm64 发行版**。树莓派版 Debian、Debian 官方
  aarch64 安装镜像、Ubuntu arm64 都不在本次范围内，它们是否同样可用未知。

## 1. 验证机环境（提取自目标机真实输出）

事实来源全部是目标机上的命令输出，不是推断。

| 项目 | 实际值 | 取值命令 |
|---|---|---|
| **发行版名** | `Armbian 26.8.1 trixie` | `/etc/os-release` → `PRETTY_NAME` |
| 底层发行版 | `Debian GNU/Linux 13 (trixie)` | `NAME` / `VERSION` |
| 版本标识 | `VERSION_ID=13`、`VERSION_CODENAME=trixie`、`DEBIAN_VERSION_FULL=13.6` | `/etc/os-release` |
| 发行版 ID | `ID=debian` | `/etc/os-release` |
| 主机标识 | `ARMBIAN_PRETTY_NAME="Armbian 26.8.1 trixie"`（Armbian 附加字段） | `/etc/os-release` |
| **内核名** | `6.18.35-ophub` | `uname -r` |
| 内核全串 | `Linux armbian 6.18.35-ophub #1 SMP PREEMPT_DYNAMIC Wed Jun 17 14:15:20 UTC 2026 aarch64 GNU/Linux` | `uname -a` |
| 内核编译器 | `aarch64-none-linux-gnu-gcc (Arm GNU Toolchain 15.2.Rel1 (Build arm-15.86)) 15.2.1 20251203` | `/proc/version` |
| **CPU 架构** | `aarch64`（dpkg 架构名 `arm64`） | `uname -m` / `dpkg --print-architecture` |
| CPU | `ARM Cortex-A53` × **8 核**（`ARMv8 Processor rev 4 (v8l)`），100–1512 MHz | `lscpu` / `/proc/cpuinfo` |
| **板卡（设备树）** | `Octopus Planet` | `/proc/device-tree/model` |
| SoC compatible | `amlogic,q200` | `/proc/device-tree/compatible` |
| Armbian 板型记录 | `BOARD="S912"`、`BOARD_NAME="Aml.S912"`、`BOARDFAMILY="meson-gxm"`、`LINUXFAMILY="amlogic"`、`ARCH=arm64` | `/etc/armbian-release` |
| **启动方式** | **无 EFI、无 DMI**，U-Boot + 设备树 | `/sys/firmware/efi`、`/sys/class/dmi` 均不存在 |
| 虚拟化 | 无（物理板，非容器非虚机） | `systemd-detect-virt` → `none` |
| 温度源 | `thermal_zone0` = `cpu-thermal`（实测 44.0 ℃）、`hwmon0` = `scpi_sensors` | `/sys/class/thermal/*`、`/sys/class/hwmon/*` |
| 有线网卡 | `eth0`（altname `end0`） | `ip -o link` |
| APT 架构 | `APT::Architecture "arm64"`，无外来架构 | `apt-config dump` |
| 资源 | 8 核 / 1787 MB 内存 / 根分区 6.5 GB | `nproc` / `free -m` / `df -h /` |

> 关于 SoC 的一点说明，照实记录差异：设备树的 `compatible` 写的是
> `amlogic,q200`，而 Armbian 的板型记录是 `S912 / meson-gxm`（Amlogic S912
> 正是 meson-gxm 家族）。两者指向同一个 SoC 家族，只是来源不同 —— 前者是内核
> 设备树由 bootloader 提供，后者是 Armbian 构建配置里的板型声明。
> drouter 面板显示的是设备树那一套。

## 2. 在目标机上的实测结果

### 2.1 构建：`.deb` 一次通过

```bash
bash packaging/build-deb.sh
```

```
== 4/6 校验 ==
  后端模块 14 个、语法全部通过
  systemd 单元 6 个齐全
== 5/6 构建 ==
dpkg-deb: building package 'drouter' in '.../drouter_1.0.10_all.deb'.
```

产物 `drouter_1.0.10_all.deb`，**753 396 字节**，`Architecture: all`。
包里 `docs/07-arm64-适配说明.md` 也在（随 deb 进 `/opt/drouter/docs/`）。

> `Architecture: all` 是关键：drouter 是纯 Python + 原生 JS，没有编译产物，
> 因此**同一个 deb 在 amd64 与 arm64 上通用**，不需要分架构重建本体。
> 真正分架构的只有「离线依赖包」（见 2.5）。

### 2.2 依赖自检：`depcheck op=check` 正常

```
自检完成：42 项已就绪，5 项缺失，26 项可选未装      # 合计 73 项
extra: {"os": "Armbian 26.8.1 trixie", "os_id": "13", "desktops": [], "has_desktop": false}
```

发行版被正确识别成 `Armbian 26.8.1 trixie`，版本号读出 `13` 且按 trixie 核对通过
（`offline-install.sh` 就是看 `VERSION_CODENAME` 这一项做版本匹配的）。

**5 项必需的缺失项**（这台机器本身没装路由相关软件包，属预期，不是适配问题）：

| 缺失项 | 对应包名 |
|---|---|
| radvd（IPv6 RA） | `radvd` |
| dhcpcd（DHCPv6 客户端） | `dhcpcd-base` |
| pppd（PPPoE 拨号） | `ppp` |
| miniupnpd（UPnP） | `miniupnpd` |
| conntrack（连接跟踪） | `conntrack` |

### 2.3 配置渲染：`render_text`（只渲染，不落盘）

按 `backend/render.py` 的 `RENDERERS` 真源逐个渲染，全部成功：

渲染方式是 `render(模块, {})` —— **空配置**。结果分两类：

| 模块 | 输出 |
|---|---|
| `chrony` | 8 行 / 170 字符 |
| `dhcpv6` | 12 行 / 168 字符 |
| `miniupnpd` | 16 行 / 425 字符 |
| `nfs` | 5 行 / 99 字符 |
| `nft_v4` | 44 行 / 1406 字符 |
| `nft_v6` | 35 行 / 1257 字符 |
| `radvd` | 22 行 / 517 字符 |
| `samba` | 22 行 / 637 字符 |

| 模块 | 空配置下的响应 |
|---|---|
| `dnsmasq` | `LAN 接口不能为空` |
| `network` | `WAN 网卡不能为空` |
| `ppp` | `PPPoE 网卡不能为空` |

这三条是**必填项校验**在起作用（`render.py` 的 `ValidateError`），不是渲染失败 ——
**与架构无关**，在 amd64 上喂同样的空配置会得到一模一样的三句话。
判据里把这三句写死成期望值，为的是反过来抓「校验本身挂了」的情况：
真出了 `ImportError` / `KeyError` 那类才算问题。

### 2.4 修复前后对比（本轮真正改掉的东西）

| 探测项 | 修复前在本机的输出 | 修复后 |
|---|---|---|
| 固件类型 | `传统 BIOS` ❌ | `设备树 (Device Tree)` ✅ |
| 厂商 | 空 ❌ | `Octopus Planet` ✅ |
| 固件枚举 | 无 | `fw_type: "dt"`、`is_dt: true` ✅ |

这是本轮**唯一一个在 arm64 上必然报错的功能点**，详见第 3 节。

### 2.5 WireGuard 四态：正好踩中「裸 `.ko`」那一档

```json
{
 "state": "need_module",
 "mod_loaded": false,
 "mod_file": "/lib/modules/6.18.35-ophub/kernel/drivers/net/wireguard/wireguard.ko",
 "tool": true, "kernel": "6.18.35-ophub", "fixable": true
}
```

值得一记：`helper` 里查模块文件的三种扩展名（`.ko` / `.ko.xz` / `.ko.zst`），
在这台 **ophub 内核**上命中的是**裸 `.ko`** —— Debian 官方内核通常是压缩过的
`.ko.xz`。如果当初只按 Debian 默认形态写一种，这台机器就会被误判成
「内核不支持 WireGuard」。这条不是本次改出来的，是被这台机器**佐证**了。

### 2.6 想在自己的板子上复验？

仓库里留了一份只读验收脚本 `devtools/verify-arm64.py`，上面 2.1–2.5 这几项
都写在里面了，在自己的 arm64 机器上一跑就有结论：

```bash
python3 devtools/verify-arm64.py            # 源码树 = 仓库根目录
python3 devtools/verify-arm64.py /opt/drouter   # 也可以指向已安装的位置
```

它只干「能不能跑」这件事：**不装包、不写配置、不起服务、不动网络**。
退 0 就是全通过。没DMI 也没 EFI 的机器它会坚持要判成设备树；
有 EFI 的机器（比如以 EFI 启动的树莓派）它按 EFI 那一档去核。

> ⚠️ 它**不**验「当路由器实际转发起来行不行」。那要点面板上的「应用」，
> 会真的改网卡、起服务 —— 别在跑着业务的机器上试。

## 3. 代码改动清单

| 文件 | 改动 | 为什么必须改 |
|---|---|---|
| `backend/drouter-helper.py` | `_read_bios()` 增加**设备树分支**；新增 `_dt_read()`、`DT_MODEL_PATHS`、`DT_COMPAT_PATHS`；返回结构加 `fw_type` / `is_dt` / `compat`，无 DMI 时拿设备树板名顶替厂商 | ARM 板没有 EFI 也没有 DMI，原代码把它们一律落到 else 分支写成「传统 BIOS」，面板上是**错的**信息。判据顺序刻意排成 EFI → 设备树 → BIOS：树莓派这类既能 EFI 又能设备树启动的机器要优先认 EFI |
| `web/i18n.js` | `bt.SYSINFO_NOTES` 增加 `设备树 (Device Tree)` 词条（`n` / `d` 两段英文） | 后端新增的展示串必须登记，否则英文界面直接漏出中文（项目 i18n 约定） |
| `backend/drouter-update.py` | 新增 `_deb_arch()`、`build_assets()`；`ASSETS` 由 `build_assets()` 生成；离线包文件名模板改为 `drouter-{ver}-offline-<本机架构>.tar.gz`；`asset_list()` 增加 `arch_specific` 标志；`apply_update()` 对带架构后缀的附件**先拿 SHA256SUMS 清单核对**，没有就明确报错 | 原先模板写死 `-offline-amd64`，arm64 机器点「一键更新」会下载一份 x86 离线包，白传几十 MB 才在装包阶段失败。清单核对让它在**下载之前**就报清楚 |
| `packaging/build-offline-bundle.sh` | 头部产物说明、塞进包里的 `README-离线安装.md` 两处的 `amd64` 改为 `$ARCH`；结尾打印架构提示 | 包名早就是 `$ARCH` 拼的，但说明文档写死 amd64 —— arm64 上打出来的包里带着一份「本机是 amd64」的说明，用户照着排查会走偏 |
| `packaging/build-docker.sh` | 新增可选第 2 个参数 `[arch]`；与本机架构不同时加 `docker build --platform linux/<arch>`，镜像标签带 `-<arch>` 后缀；dist 附件渲染用 `$IMGTAG` | Docker 镜像是分架构的。不传第 2 参数时行为**与改动前逐字节一致**（原生构建、标签不带后缀），不影响现有发版流程 |

### 关于 Docker 的一条重要提醒

Release 里发布的 `drouter-<版本>-docker.tar` 仍然是 **amd64** 镜像。
arm64 机器请走 **`deb` / 离线包** 这两条路；要用容器形态，需要在自己的 arm64
机器上 `bash packaging/build-docker.sh <版本> arm64` 自行重建
（Release 里没有 arm64 镜像附件）。

## 4. 给自己手上的 arm64 发行版打包

### 4.1 本体 deb（架构无关，推荐）

直接在目标机上构建即可，无需交叉：

```bash
git clone https://github.com/liuzhuohua/drouter.git
cd drouter
bash packaging/build-deb.sh           # → dist/drouter_<版本>_all.deb
sudo apt install ./dist/drouter_<版本>_all.deb
```

### 4.2 离线包（**必须在同架构的机器上构建**）

```bash
bash packaging/build-offline-bundle.sh
# → dist/drouter-<版本>-offline-<架构>.tar.gz
```

架构取自 `dpkg --print-architecture`。⚠️ 包里几百个 `.deb` 全是某一 CPU 的二进制，
**不能**拿 amd64 机器上打出来的包给 arm64 用。要在 arm64 上出包，
就在 arm64 机器上跑这条命令（或用 qemu-user-static chroot）。

### 4.3 Docker 镜像

```bash
bash packaging/build-docker.sh <版本> arm64     # → drouter:<版本>-arm64
docker save drouter:<版本>-arm64 -o drouter-<版本>-docker-arm64.tar
```

交叉构建依赖宿主机的 `binfmt_misc` / buildx qemu 支持；没有的话请直接到 ARM 主机上构建。

## 5. 已知限制

1. **端到端未验证**：本轮没有真的启用 Web 面板与常驻服务，也没有下发 nft / dnsmasq
   配置，因此「当路由器实际转发」这一层在 arm64 上尚无实测结论。
2. **样本只有一台**：只验证了这个发行版这一个组合；别的 arm64 Debian 系
   （含树莓派内核、Debian 官方 aarch64 内核）没有验证。
3. **依赖需自行补齐**：目标机上 radvd / ppp / miniupnpd / conntrack / dhcpcd-base
   未装（系统本身没带），面板「依赖自检」页可以逐项安装。
4. **Release 的离线包与 Docker 镜像仍是 amd64**：arm64 用户要么用 `deb` 本体
   （`Architecture: all`，通用），要么按第 4 节自行重建。
5. **x86 专属能力在 ARM 上天然不可用**：`dmidecode`（BIOS/主板/内存详情）、
   `lm-sensors` 的经典 x86 温度通道等。这些项在依赖自检里本来就是「可选」，
   缺失不影响主流程；本次把这类 x86 专属依赖**没有**改成必需。
